# Почему OpenAI Agents SDK (а не LangChain / CrewAI)

## 1. Три критерия выбора (это твоя рамка ответа)

| Критерий | Что значит | Какое наше ограничение закрывает |
|---|---|---|
| Тонкий слой абстракций | Контроль у нас, а не у фреймворка | Локальная модель, 80k — мы не можем позволить фреймворку жечь контекст на свои прослойки |
| Явная маршрутизация | handoffs в коде, а не «магия» | Главный агент = тонкий роутер: маршрут детерминирован и известен заранее |
| Трассировка из коробки | Видно «кто из субагентов что делал» | NDA: аудит «кто трогал какие данные» — обязателен |

## 2. Сравнительная таблица

| Ось | LangChain | CrewAI | OpenAI Agents SDK |
|---|---|---|---|
| Толщина абстракций | Огромный слой (chains, LCEL, memories…) | Высокоуровневый (crew/agent/task) | Тонкий: agent + handoff + tool |
| Видимость control flow | Скрыт за цепочками/графами | Скрыт за «экипажем», агенты сами решают | Явный граф handoff'ов в коде |
| Отладка | Лучшая наблюдаемость = LangSmith — ОБЛАКО (нарушает NDA) | Сторонние инструменты, самопис | Трассировка из коробки, локально |
| Типизация инструментов | Разнородно, часто строки | Есть, но высокоуровнево | Pydantic-схемы, строго типизировано |
| Роутинг | LLM-решения внутри цепочек | Авто-процессы (непредсказуемо) | Явные handoffs, детерминированно |
| Локальная модель | Да, но слой абстракций усложняет дебаг | Да, overhead | Да, любой OpenAI-совместимый эндпоинт |
| Стабильность API | Частые ломающие изменения | Молодой, API меняется | Стабильнее, обратная совместимость |
| Аудит под NDA | LangSmith в облаке = минус | Самопис | Локальная трассировка «кто что сделал» — плюс |

## 3. Острые ответы с места

- **«Почему не LangChain?»** — LangChain решает проблему «много интеграций», а у нас их мало: Mattermost + локальная LLM + RAG. Мы платили бы за слой абстракций, который прячет control flow. А лучшая наблюдаемость (LangSmith) — облачная, что прямо нарушает наш периметр NDA. Это не «не взяли», это «критерий №3 отсекает».
- **«Почему не CrewAI?»** — CrewAI навязывает модель «экипажа»: агенты сами решают, кому передать задачу. Это непредсказуемая маршрутизация, а под NDA мы обязаны знать, какой субагент и какие данные трогал. CrewAI экономит код, но забирает контроль над оркестрацией — ровно то, что мы защищаем (главный агент = тонкий роутер).
- **«Ты взял первое, что попалось!»** — «Я выбирал не по хайпу, а по скорингу на три критерия: тонкий слой, явный роутинг, трассировка. SDK закрыл все три, LangChain и CrewAI — нет. Что он попался первым, а не двадцатым, — вопрос порядка проверки, а не случайности. Возьмите мои три критерия и проскорингуйте любой фреймворк — результат тот же».
- **«А не переписать ли на X?»** — «Фреймворк — сменная деталь, архитектура — нет. Все субагенты и инструменты — наш код поверх SDK; перенос на другой фреймворк — вопрос недели. Мы защищаем архитектуру „главный + субагенты“, а не конкретный SDK — это решаемый и обратимый выбор».

## 4. Цепочка решений (для слайда-обоснования)

`NDA → данные не покидают периметр → локальная модель (qwen3.5-coder) → лимит 80k (вход+выход) → нельзя закинуть всё в контекст → главный агент + N узких субагентов (каждый промпт влезает в 80k) → нужен фреймворк с явной маршрутизацией и трассировкой → OpenAI Agents SDK (handoffs + типизированные инструменты + локальная трассировка)`.

## 5. Метрики под этот выбор

- Латенси на запрос: **+X** (каждый субагент узкий, worst case известен)
- Точность: **+Y** (в контекст не попадает лишнее)
- Итерации «спросил-поправил»: **−Z** → время до **верного** ответа падает
- Ключ: под NDA ошибка дорога (неверный расчёт ТП = брак, а не «переспросить») — точность важнее пары секунд.

*Заполни X/Y/Z своими замерами — это будет самая сильная цифра защиты.*
