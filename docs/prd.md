# PRD: CONTROL ROOM (inline-vibe)

## Executive Summary

**CONTROL ROOM** — система древовидного диалога с LLM-агентом через markdown. Пользователь пишет сообщения в ` ```agentsmindmap ` блоке внутри любого `.md` файла, watcher отслеживает изменения через inotify, и AI-агент отвечает, встраивая `🤖` узлы в то же дерево. Пользователь пишет `*` для заметок (mind map без агента) и `*?` для вопросов агенту — препроцессор заменяет их на `👤` и `👤❓` соответственно.

Главная идея: **весь диалог и память — один git-трекаемый markdown-файл**. Никакой базы данных, никакого чат-UI, никакого веб-сервера. Редактор + файл + watcher = минимальный полный интерфейс агента.

Проблема, которую решает продукт: беседа с LLM в плоском чате теряет структуру — параллельные темы смешиваются, история не ветвится, контекст размывается. Древовидный диалог держит каждую тему в своей ветке; `👤`/`👤❓` (пользователь) и `🤖` (агент) — маркеры узлов. `[hide]` и `[archive]` управляют видимостью и размером файла без вызова LLM; `.graph.json` sidecar хранит полное дерево даже поверх скрытых веток.



## Marker Format

| Ввод пользователя | Препроцессор | Назначение | Вызов агента? |
|-------------------|-------------|-----------|---------------|
| `* текст` | → `👤 текст` | Заметка (mind map) | Нет |
| `*? текст` | → `👤❓ текст` | Вопрос агенту | **Да** |
| `👤 текст` | → `👤 текст` | Заметка (уже обработана) | Нет |
| `👤? текст` | → `👤❓ текст` | Вопрос (ASCII `?`) | **Да** |
| `👤❓ текст` | → `👤❓ текст` | Вопрос (уже обработан) | **Да** |
| `🤖 текст` | → `🤖 текст` | Ответ агента | — |

**ASCII vs Unicode `?`**: пользователь может использовать клавиатурный `?` (ASCII 0x3F) —
препроцессор распознаёт `*?` и `👤?`, сериализатор всегда выводит красивый Unicode `❓` (U+2753).

**Миграция со старых маркеров**: `*` → `👤`, `[*]` → `🤖`. Парсер принимает оба формата
(старый и новый) для обратной совместимости. Сериализатор выводит только новый формат.
При первом проходе вотчера `.md` файл автоматически переписывается с новыми маркерами.

## Background & Context

Проект вырос из потребности в «лёгком» интерфейсе AI-агента для инженерной работы — код-ревью, архитектурные обсуждения, планирование. Текстовый редактор — основной инструмент разработчика, поэтому интерфейс в виде markdown-файла естественен.

Ключевые инсайты, найденные в процессе разработки:
- **Плоский лог теряет структуру**: в чат-интерфейсе нельзя ответить на сообщение трёхдневной давности, не переключив контекст. Дерево решает это.
- **LLM-вызовы дороги**: `[hide]` и `[archive]` обрабатываются препроцессором — мгновенная реакция, ноль токенов.
- **NDA/локальные модели**: система не зависит от облачных API — любой OpenAI-совместимый эндпоинт, включая локальные модели (qwen, llama, deepseek).

Выбор OpenAI Agents SDK (а не LangChain/CrewAI) задокументирован в [ideas/framework-choice.md](../ideas/framework-choice.md): тонкий слой абстракций, явная маршрутизация handoff'ов, локальная трассировка.

## User Personas

### Разработчик-инженер
- **Кто**: пишет код, обсуждает архитектуру, делает код-ревью
- **Цели**: быстрый доступ к AI-ассистенту без переключения из редактора; структурированные обсуждения сложных тем; история диалога в git
- **Боли**: чат-интерфейсы требуют копипасты кода; контекст теряется между сессиями; параллельные темы смешиваются
- **Сценарий**: открыл `CONTROL_ROOM.md` в редакторе, написал `* Как переписать этот модуль?` — агент прочитал код через `read_file()` и ответил веткой `[*]`

### Технический менеджер/Архитектор
- **Кто**: принимает архитектурные решения, ревьюит дизайн
- **Цели**: видеть цепочку решений; архивировать завершённые обсуждения; искать по истории
- **Боли**: решения теряются в чатах; нет одного источника истины по архитектуре
- **Сценарий**: просматривает дерево в `CONTROL_ROOM.md`, видит свёрнутые `[hide]` ветки, archivирует устаревшие обсуждения

### AI-исследователь/Prototyper
- **Кто**: экспериментирует с агентами, промптами, инструментами
- **Цели**: быстро прототипировать агентное поведение; делегировать подзадачи worker-у
- **Боли**: фреймворки типа LangChain добавляют слишком много абстракций
- **Сценарий**: добавляет новый инструмент в `agent.py`, тестирует через `CONTROL_ROOM_TEST.md --once`

## User Flows

### Основной цикл: пользователь → агент → ответ

```
1. Пользователь открывает CONTROL_ROOM.md в редакторе
2. Добавляет узел: `*? Привет, что можешь сказать об этом проекте?`
3. Сохраняет файл
4. watcher.py обнаруживает изменение (inotify)
5. _sync_graph(): парсинг .md, загрузка .graph.json, merge
   - Если diff состоит только из [hide]/[archive] → шаг 8 (без LLM)
6. compute_diff(old, new) → diff передаётся агенту
7. Агент читает дерево (read_mindmap), анализирует diff, вызывает add_reply()
   - add_reply обновляет .graph.json и перерендеривает .md
8. Готово — пользователь видит ответ в редакторе
```

### Скрытие ветки (без LLM)

```
1. Пользователь добавляет [hide] к узлу:
   `*[hide] Архивное обсуждение`
2. Сохраняет файл
3. watcher обнаруживает изменение
4. _sync_graph: парсит маркер [hide], обновляет .graph.json,
   перерендеривает .md (ветка схлопнута в строку-резюме)
5. LLM НЕ вызывается — время реакции < 1 мс
```

### Архивация ветки

```
1. Пользователь добавляет [archive] к узлу:
   `*[archive: устарело] Старое обсуждение`
2. Сохраняет файл
3. watcher → _sync_graph: парсит маркер
4. archiver.archive_branch():
   - One-shot LLM (не CONTROL ROOM агент!) суммаризирует поддерево
   - Полное поддерево пишется в archive/<node_id>_<timestamp>.md
   - В .md остаётся строка `*[hide] резюме`
   - .graph.json актуализируется (дети удалены)
5. Восстановление: удалить [archive] → restore_branch() из archive/
```

### Альтернативные пути и error states

- **LLM недоступна**: агент возвращает ошибку, пользователь видит сообщение в консоли watcher. Файл не повреждается — изменения ждут следующего прохода.
- **Парсинг сломан** (невалидный markdown): `parse_mindmap()` возвращает пустое дерево или частичный парсинг; агент сообщает о проблеме.
- **Файл удалён во время работы**: watcher логирует ошибку и продолжает вотчить директорию; при создании нового файла — подхватывает.
- **Гонка: пользователь редактирует во время ответа агента**: `_sync_graph()` merge-ит изменения; UUID защищают от потери данных; агент работает с состоянием на момент запуска.



## `?` Trigger — Detailed Mechanics

### Поток обработки вопроса

```
1. Пользователь пишет *? вопрос → сохраняет файл
2. watcher: inotify → _sync_graph()
3. Парсер: *? → QUESTION_RE match → has_question=True
4. merge_md_into_graph: копирует has_question из .md в граф
5. run_once: has_pending_questions(new_graph) → True
6. Агент вызывается, читает дерево, находит 👤❓ узлы
7. Агент отвечает через add_reply() → создаёт 🤖 узел-ребёнок
8. run_once: _sync_graph() вызывается повторно для cleanup
9. Cleanup: old_questions (до ответа) ∩ answered (с agent-детьми) → has_question=False
10. Сериализатор: 👤❓ → 👤 (❓ снят)
```

### Алгоритм cleanup (в _sync_graph)

```python
# ДО merge: сохраняем множество узлов с ? из предыдущего цикла
old_questions = {n.id for n in full.all_nodes() if n.has_question}

# merge: копирует has_question из .md (пользователь мог добавить новый ?)
merged = merge_md_into_graph(full, md_tree)

# ПОСЛЕ merge: чистим только те ?, которые БЫЛИ в предыдущем цикле
for node in merged.all_nodes():
    if node.has_question and node.is_user:
        if any(child.is_agent for child in node.children):
            if node.id in old_questions:  # ← ключевая проверка
                node.has_question = False
```

**Почему `old_questions` сохраняется ДО merge**: `merge_md_into_graph` мутирует `full`
in-place — после merge `full` и `merged` указывают на один объект. Если проверять
`full.get_node()` после merge, получим уже смерженное состояние, а не старое.

### Edge Cases

| Сценарий | Поведение |
|----------|----------|
| `*?` на узле с существующими ответами агента | `?` **сохраняется** — пользователь задаёт follow-up вопрос |
| `*?` на новом узле без ответов | `?` сохраняется, агент вызывается |
| Агент ответил → следующий цикл вотчера | `?` снимается (если был в `old_questions`) |
| `*` без `?` (mind map) | Агент не вызывается, даже если есть другие pending questions |
| Пользователь редактирует `👤❓` → `👤` (убирает `?`) | `has_question` → False, агент не вызывается |
| Двойной `?` (`*??`) | Не распознаётся — QUESTION_RE требует ровно один `?` |
| `🤖?` (агент с вопросом) | `has_question` = False (только user-узлы могут быть вопросами) |

## Non-Functional Requirements

- **Performance**:
  - Парсинг/сериализация: < 10 мс для файла до 10K строк
  - `?` trigger — вызов агента только при явном вопросе (`*?` → `👤❓`): < 1 мс (без LLM)
  - Вотчер: реакция на изменение < 100 мс (inotify)
  - LLM-ответ: зависит от модели, не регламентируется системой
- **Security**:
  - API-ключи через `.env` (в `.gitignore`)
  - `read_file()` блокирует выход за пределы project root
  - `run_shell()` ограничен таймаутом (30 с по умолчанию)
  - Трассировка отключена по умолчанию (`DISABLE_TRACING=1`)
- **Compatibility**:
  - Python ≥ 3.14
  - Linux (inotify), macOS (FSEvents), Windows (ReadDirectoryChangesW) — через watchfiles
  - Любой OpenAI-совместимый эндпоинт (OpenAI, DeepSeek, локальные модели через vLLM/LiteLLM)
- **Reliability**:
  - `.graph.json` sidecar гарантирует сохранность скрытых данных
  - `archive/` директория хранит полные поддеревья
  - UUID защищают от коллизий при merge

## `[focus]` — Focus Mode (v1.1)

### Назначение

Пользователь может «сфокусироваться» на одной ветке дерева — визуально она становится
корнем отображения, весь остальной mind map скрывается из `.md`. Полный граф при этом
сохраняется в `.graph.json` и восстанавливается при снятии фокуса.

### Синтаксис

```
👤[focus] Заголовок сфокусированной ветки
```

Старый формат (обратная совместимость):
```
*[focus] Заголовок сфокусированной ветки
```

### Правила

- Только **один** узел может быть в фокусе одновременно. Новый `[focus]` снимает старый.
- `[focus]` — preprocessor-only: добавление/снятие не вызывает LLM (как `[hide]`).
- Фокус **не меняет граф** — это чисто view-фильтр. `.graph.json` всегда хранит полное дерево.
- При активном фокусе `.md` содержит **только** сфокусированное поддерево.
- При снятии `[focus]` полное дерево восстанавливается из `.graph.json`.
- `[focus]` имеет приоритет над `[hide]`/`[archive]`: сфокусированная скрытая ветка
  показывается, но дочерние `[hide]` внутри поддерева сохраняются.

### Поток данных

```
1. Пользователь: 👤[focus] Ветка X
2. _sync_graph: парсер → node.focused = True
3. Сериализатор: focused_node существует →
   выводит ТОЛЬКО поддерево focused_node как визуальный корень
4. .md содержит только сфокусированную ветку
5. .graph.json содержит полное дерево
6. Пользователь убирает [focus]:
7. _sync_graph: focused_node = None
8. Сериализатор: полное дерево из .graph.json → .md
```

### Пример

**Полное дерево (.graph.json):**
```
root: My Project
👤 Архитектура
  🤖 Используем микросервисы
👤[focus] Баг: падает на старте
  👤❓ Как дебажить?
    🤖 Проверь логи в /var/log
👤 Рефакторинг
```

**.md при активном фокусе:**
```
root: Баг: падает на старте
👤❓ Как дебажить?
  🤖 Проверь логи в /var/log
```

### Реализация

| Компонент | Изменения |
|-----------|----------|
| `MindNode.focused: bool` | Новое поле (default=False) |
| `FOCUS_RE` | `r"^(👤\|🤖\|\*\|\[\*\])\[focus\]\s"` |
| `_parse_block()` | Приоритет: QUESTION_RE → FOCUS_RE → HIDE_RE → ... |
| `MindTree.focused_node` | `@property` — возвращает узел с `focused=True` или None |
| `to_outline()` | Если `focused_node` — рендерит только его поддерево |
| `serialize_mindmap()` | Если `focused_node` — сериализует только его поддерево как `root:` |
| `render_mermaid()` | Аналогично — только сфокусированное поддерево |
| `to_dict()`/`from_dict()` | `focused` в JSON |
| `merge_md_into_graph()` | Копирует `focused`, снимает с других узлов при новом фокусе |
| `diff_trees()` | Переключение `[focus]` не считается content change (не вызывает LLM) |
| `_sync_graph()` | При снятии `[focus]` восстанавливает полное дерево из `.graph.json` |

### Edge Cases

| Сценарий | Поведение |
|----------|----------|
| `[focus]` на скрытой (`[hide]`) ветке | Ветка показывается, фокус имеет приоритет |
| `[focus]` на архивной (`[archive]`) ветке | Ветка показывается (фокус > archive) |
| Два `[focus]` одновременно | Первый (по порядку в файле) активен, второй игнорируется |
| `[focus]` + `?` на одном узле | Оба маркера активны: `👤❓[focus]` или `👤[focus]❓` |
| Снятие `[focus]` при наличии новых узлов | `.graph.json` содержит всё → `.md` восстанавливается полностью |

### Регулярные выражения (маркеры)

| Regex | Назначение | Пример совпадения |
|-------|-----------|-----------------|
| `TAG_RE` | Обычные узлы | `👤 текст`, `🤖 текст`, `* текст`, `[*] текст` |
| `QUESTION_RE` | Вопросы агенту | `👤❓ текст`, `👤? текст`, `*? текст` |
| `HIDE_RE` | Скрытые узлы | `👤[hide] текст`, `*[hide] текст` |
| `ARCHIVE_RE` | Архивные узлы | `👤[archive] текст`, `*[archive: причина] текст` |

**Приоритет в парсере**: `QUESTION_RE` → `HIDE_RE` → `ARCHIVE_RE` → `TAG_RE`.
Вопрос проверяется первым, чтобы `*?` не был захвачен `HIDE_RE`.

## Design Decisions (архитектурный контекст)

Задокументированы для будущих контрибьюторов.

1. **Дерево, а не плоский лог**: ветвление диалога ≠ лента сообщений. Стабильные ID узлов (UUID) для адресации.
2. **`.graph.json` sidecar**: `.md` — это VIEW в граф; полное дерево (включая скрытые поддеревья) хранится в JSON. `.md` перерендеривается из графа.
3. **`[hide]` как препроцессор**: никаких LLM-вызовов на toggle видимости. Мгновенно, бесплатно.
4. **UUID вместо ordinal ID**: при merge двух версий файла ordinal ID (`root.1`, `root.1.1`) ломаются; UUID выживают.
5. **7 инструментов, не больше**: каждый инструмент покрывает одну операцию над деревом или средой. Никаких «универсальных» инструментов — агент должен явно выбирать действие.
6. **OpenAI Agents SDK вместо LangChain**: тонкий слой, явный control flow, локальная трассировка. Подробный анализ в [ideas/framework-choice.md](../ideas/framework-choice.md).
7. **Файл — источник истины**: система stateless между проходами. Всё состояние — в `.md` + `.graph.json` + `archive/`. Никакой БД.
8. **`?` — явный триггер агента**: `*` без `?` = режим mind map (пользователь рассуждает сам с собой, агент не вызывается). `*?` = вопрос агенту. Принимается как ASCII `?` (клавиатурный), так и Unicode `❓`. Это даёт пользователю полный контроль над тем, когда тратить LLM-токены.
9. **Cleanup с защитой от ложного срабатывания**: `❓` снимается ТОЛЬКО для вопросов, которые были активны в предыдущем цикле вотчера (`old_questions`). Если пользователь добавил `?` к узлу с существующими ответами агента (follow-up вопрос), `?` сохраняется. Это предотвращает мгновенное снятие свежепоставленного вопроса.


## Known Bugs — Fixed

### BUG-001: `❓` не снимался после ответа агента (2026-08-02)

**Симптом**: агент отвечал на `👤❓`, но маркер вопроса оставался.

**Причина**: `run_once` не вызывал `_sync_graph` после ответа агента. Cleanup происходил
только на следующем цикле вотчера, но `ctx.last_content` уже был обновлён →
вотчер видел тот же контент и пропускал цикл.

**Фикс**: `run_once` вызывает `_sync_graph(ctx)` сразу после `_remove_thinking_markers`.

**Тест**: `test_cleanup_removes_question_marker_from_file` — проверяет что `👤❓` → `👤` на диске.

### BUG-002: Свежий `?` снимался на узлах с существующими ответами (2026-08-02)

**Симптом**: пользователь ставил `?` на узел, где агент уже отвечал ранее (follow-up вопрос),
но `?` мгновенно снимался препроцессором.

**Причина**: cleanup проверял наличие agent-детей, но не учитывал, что `?` мог быть
только что добавлен пользователем. `merge_md_into_graph` мутирует `full` in-place,
поэтому проверка `full.get_node()` после merge возвращала уже смерженное состояние.

**Фикс**: множество `old_questions` сохраняется ДО merge. Cleanup чистит только те `?`,
чей ID есть в `old_questions` (т.е. вопрос был активен в предыдущем цикле).

**Тест**: `test_fresh_question_kept_with_existing_replies` — follow-up `?` на узле
с существующим ответом агента сохраняется.
